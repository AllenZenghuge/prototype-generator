## 决策时间线

### 1. 产品范围
- **决策**: 先做 X，后续扩展小红书、抖音
- **原因**: X API 相对开放，实现难度最低；先跑通再扩展

### 2. 后端策略 ⚠️ 已变更（见决策 17）
- **原决策**: App + Python 后端一起做（方案 B）
- **原因**: 真实无水印解析需要后端支持（平台加密签名）
- **变更（2026-07）**: **改为 App 直连三平台**。X 直连 vxtwitter，小红书抓 HTML，
  抖音用 WebView 借平台自身的 JS 生成签名——**不再需要后端**。
  后端代码保留，作为远期上架方案（见决策 17）

### 3. 后端技术
- **决策**: FastAPI + httpx + Pydantic
- **原因**: 异步支持、类型校验、开发效率高
- **变更**: v1.1 移除 BeautifulSoup4（不再解析 HTML），改用 Pydantic 做请求/响应模型

### 4. X 解析方式
- **原始决策**: 解析公开推文页面 `__NEXT_DATA__` JSON
- **变更（v1.1）**: 改用 vxtwitter 第三方 API
- **原因**: X 页面结构变更，不再内嵌 `__NEXT_DATA__`，原方案失效。vxtwitter API 稳定且无需认证

### 5. 稳定性保障 ⚠️ 已随决策 2 变更而作废（后端侧策略）
- **原决策**: 三层反封禁策略（UA 轮换 + 频率控制 + 容错重试）
- **原因**: 用户半小时可能下载几十个视频，需要稳定
- **现状**: 后端不在主链路，该策略随之失效。App 侧的稳定性靠
  平台解耦（每个平台独立解析器）+ 失败重试（下载记录可重新下载）

### 6. 内容类型
- **决策**: 视频 + 图片 + 文案三种都做
- **原因**: X 推文经常同时包含多种内容

### 7. 操作模式
- **决策**: 单个操作（不设计批量队列）
- **原因**: 用户实际使用是「发现一个 → 粘贴 → 下载 → 再找下一个」

### 8. 视觉设计
- **方向**: 「暗房」隐喻
- **差异化**: 不用紫蓝渐变（参考 App 的方案），用暗房安全灯红作为唯一强调色
- **签名元素**: CTA 按钮的「显影」动画（0.8s 光晕呼吸）

### 9. 下载列表
- **决策**: 永久保留记录，可多次重新下载
- **原因**: 用户可能隔天回来重新下载同一个链接（直链可能过期，需要重新解析）

### 10. 文件命名
- **决策**: 用推文正文作为文件名
- **降级**: 正文为空时用 `@screenName_statusID`

### 11. 代理配置（v1.1 新增）
- **决策**: 通过环境变量 `HTTPS_PROXY` / `HTTP_PROXY` 配置，不硬编码
- **原因**: Mac 开发时需走本地代理（`127.0.0.1:7897`），iPhone 真机/VPS 线上走 VPN 直连，不应写死在代码里

### 12. 重新下载策略（v1.1 新增）
- **决策**: 重新下载 = 重新解析 + **删旧建新**（删除旧 DownloadItem + 插入新 DownloadItem）
- **原因**: CDN 直链有效期短（数小时），必须重新解析。原地修改 SwiftData `@Model` 对象存在引用/线程安全问题，删旧建新是最稳妥的方式

### 13. 下载存储路径（v1.1 新增）
- **决策**: 使用 `cachesDirectory/Downloads/` 作为下载中间路径，写入 Photos 相册后自动清理本地副本（见决策 16）
- **原因**: temp 目录随时清理，caches 更可靠；仅作中转，不长期驻留

### 14. 选择性下载（v1.1 新增）
- **决策**: 当前选中哪个 tab（视频/图片/文案），点击保存只下载该类型；不捆绑下载所有类型
- **原因**: 用户通常只需要其中一种，捆绑下载浪费时间和存储

### 15. 媒体项勾选（v1.1 新增）
- **决策**: 视频/图片列表每项加复选框，默认全选，可逐个取消勾选，只下载选中的项
- **原因**: 一条推文可能包含多个视频/图片，用户可能只想要其中一部分

### 16. 存储策略 — 只存相册不存双份（v1.1 新增）
- **决策**：下载文件写入 Photos 相册后立即删除本地缓存，不保留双份
- **原因**：DCIM 相册是用户唯一需要的副本，再存一份到 Caches 纯属浪费空间
- **降级**：写入相册失败时保留本地文件，确保不丢数据

### 17. 架构改 App 直连（2026-07 新增，覆盖决策 2）

- **决策**: 砍掉后端，App 直连各平台
- **原因**:
  - 后端部署/运维成本高，个人工具没必要
  - 小红书抓 HTML 不需要签名；抖音可借页面自身的 JS 生成签名
  - 用户明确「翻墙是手机 VPN 的事，后端不提供翻墙」
- **远期**: 若上架 App Store，计划改为「X 直连 + 小红书/抖音走国内服务器后端」

### 18. 抖音解析 — 借平台 JS 签名（2026-08 新增）

- **决策**: 隐藏 WKWebView 加载页面，注入 JS hook 拦截 `aweme/detail` 响应
- **放弃的方案**: 自建 `a_bogus` 签名算法
- **原因**: 自建约 300 行且**约两周失效一次**；借平台自己的 JS 签名可自动适配
- **关键约束**: **必须伪装桌面 Chrome UA**——移动 UA 会被带到
  `iesdouyin.com/share/...` 的「打开抖音 App」引导页，该页**不请求 detail 接口**，
  hook 永远等不到响应

### 19. 图集内容分类（2026-09 新增）

- **决策**: 图集项按 `live_photo_type` / `clip_type` 分为三类，分别处理
  - `live_photo_type == 1` → 实况照片（静态图 + 两三秒伴随片段）
  - `clip_type == 4` → **独立短视频片段**（本质是短视频，只是挂在图集里）
  - 其余 → 普通静态图
- **原因**: 此前一律按图片下载，**17 个视频片段只得到 17 张静态封面**
- **界面**: 图片页在含视频片段时提供「图片 / 视频」二选一，选视频后可合并成一个

### 20. 实况照片合成（2026-09 新增）

- **决策**: 自己把「静态图 + 动态片段」缝成相册认得的配对资源
- **要点**:
  - 图片写 EXIF `MakerApple["17"]`，**标识必须 36 字符 UUID**
    （ImageIO 会把不足 36 位的用 `.` 补齐，导致配不上）
  - 视频写 `com.apple.quicktime.content.identifier` + `still-image-time` 元数据轨
    （**值是 `0xFF` 不是 `0`**）
  - 静态图**必须转成 JPEG**（抖音给的是 webp，相册不收）
- **失败降级**: 退回「静态图 + 独立视频」，素材不丢，**原因写进记录（不静默）**

### 21. 音视频必须并行推进（2026-09 新增，踩坑最久的一条）

- **问题**: 实况照片合成长期卡在「视频轨无进展」
- **根因**: `AVAssetWriter` 要求**所有 input 的数据按时间交错推进**。
  我串行写（先写完视频再写音频），writer 一直等落后的那一轨，
  **两个 input 都永远 `isReadyForMoreMediaData = false`**
- **决策**: 用 `async let` **并行**推进音视频两个 pump
- **中间弯路**: 曾靠「去掉音轨」绕过（代价是静音），但那是回避而非解决

### 22. 并行时音轨用独立 reader（2026-09 新增）

- **问题**: 恢复声音后，实况照片全部退化成普通短视频
- **根因**: 两个 pump **共用一个 `AVAssetReader`**。reader 及其 output
  **不是线程安全的**，并发 `copyNextSampleBuffer` 会竞态
- **决策**: 音轨用**独立的 reader**（每个 reader 只管一条轨）
- **教训**: 「writer 支持并发 append」**不等于**「reader 也支持并发读取」——
  并行化前先确认被并发访问的对象是否线程安全

### 23. 相册权限只要写入（2026-09 新增）

- **决策**: `Info.plist` **只声明** `NSPhotoLibraryAddUsageDescription`，
  代码中**禁止** `PHAsset.fetch*`
- **原因**: `fetch*` 需要「读取相册」权限。**越权调用不会被拒绝或抛错，
  而是被 TCC 直接 abort 掉整个进程**（`___TCC_CRASHING_DUE_TO_PRIVACY_VIOLATION___`）
- **教训**: 不要为了「锦上添花」的校验去要多余权限——
  那次回读校验先后制造了「多存一张图」和「真机崩溃」，最后整个删掉
- **加固**: `TC-PERM-01` 扫描源码防回归

### 24. 下载任务按图集项拆分（2026-09 新增）

- **决策**: `DownloadItem` 记录 `galleryClipIndex`（该项在图集里的序号）
- **原因**: 重新下载要重新解析拿新鲜地址，而图集片段/图片的地址都不在顶层
  `videos` 里。没有序号会导致：视频片段任务报「已无可用媒体」、
  点一张图重新下载把整个图集（50 张）重下一遍
- **例外**: 批量解析建的打包任务序号为 nil，仍整体重下（这是对的）

### 25. 验证必须覆盖真机（2026-09 新增）

- **决策**: 涉及 `LivePhotoBuilder` / `VideoMerger` / `DouyinWebParser` /
  权限相关的改动，**模拟器通过不算数，必须真机验证**
- **原因**: 实况照片这条路上，「模拟器全绿、真机失败」出现过至少三次
  （`Task.detached`、轮询 pump、共用 reader）
- **流程**: 这类改动**先在分支上做**，验证通过再合主线
